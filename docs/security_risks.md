# Registre des risques — tâche 11

Gravités qualitatives, pas des probabilités mesurées. P0 : prérequis bloquant avant l’usage concerné ; P1 : amélioration prioritaire ; P2 : amélioration planifiée. Les protections sont vérifiées au niveau code/tests sauf mention contraire. Aucun risque n’est accepté au nom de la propriétaire. Responsable proposé : responsable du projet.

| ID / risque | Gravité démo / production | Impact | Protection existante | Recommandation / priorité |
| --- | --- | --- | --- | --- | --- |
| R01 — Identité et rôles simulés | Modérée / Critique | Tout visiteur peut choisir administrateur ou un autre client ; impropre à des données réelles. | Contrôles métier corrects pour le contexte fourni, avertissements UI, données synthétiques. | Authentification serveur, rôles non modifiables par le navigateur, liaison client/compte et tests multi-tenant. **P0 avant production** |
| R02 — Groq public et abus | Élevée si configuré / Critique | Épuisement de quota, dépenses ou requêtes non autorisées si les variables rendent Groq sélectionnable. | Mock par défaut ; timeout, bornes de tokens/appels et zéro relance SDK ; CI sans clé. | Garder les secrets Groq absents du site public ; avant activation : authentification, quotas, budget, limitation de débit et arrêt d’urgence côté serveur. **P0 avant activation publique** |
| R03 — Injections et obfuscation | Modérée / Élevée | Les filtres lexicaux sont contournables et peuvent aussi refuser des questions légitimes. | Liste blanche de trois outils en lecture seule ; arguments stricts ; contexte séparé ; validations avant exécution. | Ne pas utiliser le filtre comme autorisation ; enrichir corpus adversarial et délimiter toute nouvelle source documentaire. **P1** |
| R04 — Confidentialité des commandes | Faible sur fixtures / Critique avec données réelles | Accès indirect aux données d’un autre client si le contexte externe est falsifié. | Vérification de propriété dans get_order_status ; refus neutre identique pour inconnu/autre client ; résultats masqués. | Contexte issu d’une identité authentifiée et non du sélecteur ; isoler stockage et accès tenant. **P0 avant données réelles** |
| R05 — Texte envoyé au fournisseur | Faible en Mock / Élevée | Le prompt et quatre questions d’historique peuvent contenir des données personnelles ou confidentielles en mode réel. | Aucun appel en Mock ; résultats métier et identité du contexte non retransmis au modèle. | Limiter/supprimer les données sensibles avant envoi, informer les utilisateurs et vérifier les conditions fournisseur avant usage réel. **P0 avant usage réel avec données personnelles** |
| R06 — Gestion des secrets | Modérée / Critique | Une exclusion Git n’efface pas un secret déjà versionné ; le scanner peut manquer un format ou un encodage. | Exclusions env/keys/logs ; exemple vide ; scan courant et historique par motifs, aucun résultat détecté. | Inventaire propriétaire des secrets distants, moindre privilège, révocation immédiate en cas de fuite, revue avant commit et rotation selon risque. **P0 si incident** |
| R07 — Conservation des traces | Modérée / Élevée | Croissance disque et perte de preuves sur redémarrage ; absence d’alerte si le logging échoue. | Pas de contenu brut ; fichier créé 0600 ; pannes non bloquantes ; logs exclus de Git. | Rotation taille/durée, indicateur d’échecs de collecte et stockage durable contrôlé avant exploitation de production. **P1** |
| R08 — Sessions et ressources publiques | Modérée / Élevée | Historique UI sans plafond de messages ni TTL ; sessions nombreuses ou longues peuvent épuiser les ressources. | 1500 caractères par question ; seules quatre questions envoyées ; reset lors du changement de contexte. | Plafond de conversation, TTL, contrôle de débit/concurrence et suppression explicite des états ; tester la charge. **P1** |
| R09 — Dépendances et code de PR | Modérée / Élevée | Code de contribution et dépendances transitives non entièrement verrouillées peuvent exécuter du code sur runner. | Actions épinglées par SHA ; contents:read ; pas de pull_request_target ; checkout non persistant ; tests sous garde réseau. | Revue des PR et dépendances, verrouillage reproductible, revue des mises à jour de SHA et des protections de branche. **P1** |
| R10 — Métadonnées et artefacts | Faible / Modérée | UUID/horodatage peuvent être recoupés ; minimisation ne signifie pas anonymat irréversible. | Traces sans texte/identité ; projection CI numérique ; rétention artefacts 3 jours. | Accès restreint aux logs runtime, n’exporter que des agrégats, contrôler régulièrement les artefacts et les droits. **P1** |
| R11 — Disponibilité et preuve du runtime | Modérée / Élevée | Redémarrages, stockage éphémère et runtime non confirmé empêchent une garantie de disponibilité ou d’attestation. | Données historiques affichées ; recette locale et cinq parcours publics rapportés par la propriétaire. | Confirmer SHA/Python dans les logs sans secrets ; prévoir disponibilité surveillée et politique de sauvegarde adaptée. **P1** |
| R12 — Qualité et couverture sémantique | Modérée / Élevée | Paraphrases non reconnues, recherche lexicale et benchmark petit ; résultats incomplets possibles. | 42/45, trois échecs visibles ; données/rendu déterministes ; refus et clarifications distincts des erreurs. | Conserver les échecs, étendre l’évaluation sans modifier les attentes pour gagner des points ; budget LLM à décider séparément. **P2** |
| R13 — Incidents et gouvernance opérationnelle | Modérée / Élevée | Pas d’astreinte, alerte ou procédure automatisée de réponse aux incidents. | Runbook documentaire et gates ; erreurs neutres côté UI et sans exception brute dans les traces. | Nommer un responsable, tester le runbook, tracer les décisions et la reprise ; ne pas copier de contenu sensible dans un ticket public. **P1** |
| R14 — Administration des plateformes | Non vérifiée / Élevée | Droits GitHub/Streamlit, MFA et inventaire des secrets distants non inspectés par cet audit. | Workflow du dépôt à permissions minimales ; aucune modification de comptes ou Secrets effectuée. | La propriétaire confirme les accès, MFA, protections de branche et absence de Groq public ; aucune valeur secrète à partager. **P1** |

Les détails, références de code et décisions à valider sont dans risk_register.json. Ce registre ne remplace pas une revue indépendante ni les prérequis d’une application réelle. Le stockage actuel ne contient que des fixtures synthétiques, publiquement versionnées ; il n’assure pas une isolation de clients authentifiés.
